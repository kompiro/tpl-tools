# ADR-27: Generate the TPL index grouped by topic, from a config-named indexFile

- **Date**: 2026-10-21
- **Status**: Accepted
- **Related**:
  - Issue #27, PR #28 (implementation), PR #29 (release v0.0.11)
  - `src/regenerate.ts`, `src/cli/regenerate.ts`, `src/config.ts`, `src/validate.ts`
  - Depends on ADR-6 (no new dependencies) and ADR-8 (`tpl.config.json` holds reference data)
  - Downstream: karasu#3289 (adoption)

## Background

`tpl validate` required the TPL directory's `README.md` to link every TPL, so
each PR that added a TPL appended a row to a hand-maintained table. TPL ids
grow monotonically (issue numbers, dates), so **every new row landed at the
same tail**, and git reports two insertions at one position as a conflict.

In karasu this was the most conflict-prone file in the repository. Of the 28
commits that touched its README between 2026-09-19 and 2026-10-19, 23 were a
single appended row; on 2026-10-19 one of four open TPL-adding PRs already
conflicted with `main` on it, and merging another would have made it conflict
again. Sorting rows by id does not help: the newest id is always the largest.

## Decision

Generate the index with `tpl regenerate [--check]` into the file named by a
new `indexFile` key in `tpl.config.json`, grouped by topic, and have
`tpl validate` check that file instead of `README.md` once the key is set.

## The output

```markdown
# TPL index

<!-- Generated by `tpl regenerate` ... -->

## Active

### renderer

- [TPL-999](TPL-999-implicit-data-filtering.md) — <title> (#999, #412)

### app-ui

- ...

## Deprecated

- ...
```

- Topics follow the order of the `topics` vocabulary, then topics outside it
  alphabetically; entries are sorted by id (numerically) within a topic.
- Each entry is the id link, the title on one line, and the `issue` values of
  `discovered_from`.
- Every TPL appears exactly once, so the generated file also passes
  `tpl validate`'s index check.

## Rationale

- **Grouping is what separates concurrent branches.** Two branches that add a
  TPL to different topics insert at different, non-adjacent lines, which git
  merges cleanly. They conflict only within one topic. On karasu's last month
  (half the new TPLs were `renderer`), that is about 30% of concurrent pairs
  against about 100% for one table, and the four PRs open on 2026-10-19 would
  not have conflicted at all. Verified in a scratch repo: `renderer` +
  `build` merged cleanly, `renderer` + `renderer` conflicted.
- **Generating makes the remaining conflicts mechanical.** A conflict in the
  index is resolved by re-running `tpl regenerate`, never by hand; `--check`
  in CI keeps a stale or hand-edited file from landing.
- **One key, read by both commands.** `regenerate` writes and `validate`
  checks whichever file `indexFile` names. `regenerate` refuses to run without
  the key rather than defaulting to a name, so the two commands can never look
  at different files.
- **Topics sit one level below `## Active`.** With topics as `##` headings, a
  topic named `Deprecated` shared the deprecated section's heading. Moving
  topics to `###` removes the collision for every name, where reserving
  `Deprecated` would have been one more rule to state and check.
- **No new dependency** (ADR-6): `node:fs` / `node:path` only.

## How much of a path `indexFile` may be

Five of the seven review rounds that requested changes on PR #28 were about
this boundary, so it is recorded here rather than left to the code. `regenerate` writes the file, so
the value must not reach outside the TPL directory, and it must not be read as
a TPL.

- **One spelling: a relative path with `/` separators.** A backslash, a leading
  or trailing `/`, an absolute path and a `..` segment are config errors. A
  backslash is a separator on Windows and a filename character on POSIX, so
  accepting it made every later check depend on the platform: two rounds in a
  row found a new spelling (`./TPL-index.md`, then `TPL-foo\bar.md`) that
  slipped past the previous fix. Narrowing what is accepted ended that class.
- **Not `TPL-*.md` directly in the TPL directory**, checked after
  `posix.normalize`, because `tpl validate` reads those files as TPLs. The
  same name in a subdirectory is fine; discovery does not recurse.
- **The real path must stay inside.** Lexical checks live in `loadReferenceData`;
  the filesystem check lives in `regenerate`, the only writer and the only
  command that knows the TPL directory. It requires the real path of the
  nearest *existing* directory on the way to be inside the real TPL directory
  (directories below it are then created by `regenerate`), and refuses an index
  file that is itself a symlink.
- **Failures are classified, not thrown.** Only ENOENT / ENOTDIR mean "no
  index"; any other read error (a directory at the path, permissions, a
  symlink loop) is reported as unreadable, because `existsSync` returns false
  for those too and would have called them missing. CRLF line endings compare
  equal to the generated LF output, so a Windows checkout is not stale.

## Rejected alternatives

- **`merge=union` on the README table.** Silences local merges, but union on a
  whole README also keeps both sides of a prose conflict, GitHub's mergeability
  check is not expected to honour a custom merge driver (not verified), and
  the table still grows by hand.
- **Not committing an index at all** (list TPLs from `tpl related` or a docs
  site). No conflicts, but the corpus is no longer browsable on GitHub, and
  `validate` loses its "every TPL is listed" check.
- **One generated, id-sorted list.** Mechanical to resolve, but every pair of
  concurrent PRs still conflicts at the tail.
- **A default `indexFile` name.** Convenient for `regenerate`, but `validate`
  would keep reading the README until the key is set, so the two would check
  different files.
- **Normalizing backslashes instead of rejecting them.** Tried in PR #28; each
  normalization left a spelling the next check read differently.

## Consequences

- Without `indexFile`, nothing changes: `validate` checks `README.md` exactly
  as in v0.0.10. Adopting the generated index is a config change plus
  `tpl regenerate --check` in CI.
- `validate`'s index check stays "every TPL is linked and every link
  resolves"; it does not compare a link's label with its target. For the
  generated file, `--check` covers that, since any edit makes it differ from
  the generated output.
- A TPL that is the first of a new topic adds a heading between two sections,
  which can still meet an insertion at the previous section's tail. That is
  rare and resolved the same way.
